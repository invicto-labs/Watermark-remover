## What is ready

- `render.yaml` defines a Python/Waitress web service with automatic deploys OFF.
- `payment_service.hosted` serves the website, checkout, webhook and online credits.
- SQLite document permissions and balances persist under `/var/data`.
- The customer EXE pins the exact public billing configuration. Missing or modified
  config and environment overrides cannot switch the packaged app into free mode.
- Razorpay builds ignore local offline licenses/usage. Every document open and
  protected API operation checks the server's authenticated credit ledger.
- New local identities have zero credits. Keeping or restoring an identity keeps
  the same server balance; changing identity cannot transfer purchases.
- Signed, request-bound balance replies prevent replaying an old credit response.
- Refund webhook events revoke that order's online document permissions.

The public code and customer computer remain under the customer's control. This
does not prevent deliberate modification of the EXE or extracting its local
processing engine. Enforceable processing limits against a modified client require
running the paid processing on a server. This implementation closes ledger rollback
and configuration deletion in the provided app; it is not tamper-proof DRM.

## Render configuration

Use the existing service only if you control it. When later authorized to deploy:

1. Select Python runtime, build `pip install -r payment_service/requirements.txt`,
   start `python -m payment_service.hosted`, health path `/health`. Turn automatic
   deployment off while reviewing changes. Match the blueprint's Python version.
2. Attach a persistent disk at `/var/data`; set `CLEARPAGE_PAYMENT_DB` to
   `/var/data/credits.sqlite3`. Render persistent disks require a paid service.
   This configuration is not compatible with free ephemeral-only SQLite storage.
3. Upload an encrypted Ed25519 key as a Render **Secret File** named
   `clearpage-signing.pem`; set its password, Razorpay key ID/secret and webhook
   secret using Render's private environment settings. Never upload the test key
   to a live service or put secrets in the Git repository or public website.
4. Keep independent test/live signing keys and databases. The database refuses a
   mismatched Razorpay key ID/signing key. Back up the database AND the keys.
5. Configure automatic capture and webhooks for `payment.captured`, `order.paid`,
   `payment.refunded`, `refund.processed` to
   `https://clearpage.onrender.com/api/webhook`. Confirm actual delivery in test
   mode before accepting money. Webhook delivery is required for timely revocation;
   don't refund outside your tracked payment workflow without reconciliation.
6. Set the customer `billing.json` to that HTTPS origin, the matching public key,
   seller name and email. Build **after** those details are correct. The EXE pins
   that exact configuration: post-build edits require rebuilding the executable.
   Customer payment access requires internet; no offline credit fallback exists.
7. Follow `AUTOMATIC-RELEASES.md` to configure the public GitHub Actions variables
   and publish an approved version tag. Each verified release includes the stable
   `ClearPage-Windows-x64.zip` asset. Website download buttons automatically follow
   GitHub's latest published stable release; no ZIP upload to Render is needed.
   The old `/downloads/ClearPage-Windows-x64.zip` route redirects to that URL and
   never serves local files. The first compatible production release must exist
   before the public download works. Nothing has been published locally.
8. Test a capture, two distinct PDFs, repeated access, blocked third PDF, local
   ledger rollback, configuration deletion, app/service restart, outage, refund,
   backup restore, native desktop exports and the latest-release download. Keep
   production sales disabled until this succeeds.

Backup example (run privately on the service):
`python scripts/backup_credit_db.py /var/data/credits.sqlite3 /var/data/backups/credits-UNIQUE.sqlite3`
The SQLite backup API creates a consistent snapshot. Treat restores as an owner
operation: old database backups can omit later payments/usage. Reconcile against
Razorpay records before reopening sales after disaster recovery.

## Optional owner admin login

`ADMIN.md` describes the app's owner panel. Add `CLEARPAGE_ADMIN_USERNAME` and
`CLEARPAGE_ADMIN_PASSWORD_HASH` only to the server's private environment to enable
it; leaving both unset disables admin access. Use the scrypt hash generated by
the private owner setup utility, never a plaintext password or default credential.
Keep these settings out of customer billing files and GitHub Actions. Sessions
expire after one hour and are installation-bound; every document request still
needs a signed online authorization. Owner access does not spend paid credits.
